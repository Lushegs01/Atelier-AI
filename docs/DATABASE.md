# Database and authorization

`supabase/migrations/202610240001_initial.sql` is an additive initial PostgreSQL migration for a fresh Supabase project. `supabase/seed.sql` contains **disabled draft retail prices** and no customer records, uploaded photos, payment events or artificial generations. Never apply migrations to an unknown existing database without backup and review.

## Local commands

```powershell
npm ci
npm run db:validate
# Docker is required by the Supabase CLI local stack:
npx supabase start
npx supabase db reset
# Configure .env.local with the printed local API keys; keep service_role server-only.
```

For a controlled staging project, link the intended project (`npx supabase link --project-ref YOUR_PROJECT_REF`), inspect the pending SQL (`npx supabase db push --dry-run`) and apply with `npx supabase db push --include-seed`. Use separate projects and keys for local/staging/production. Project ref is not an API secret. The repository does not provision a remote project or apply live migrations.

## Record model

| Tables                                      | Purpose and isolation                                                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `profiles`                                  | Auth user display name and onboarding status; clients can read their own profile and update only permitted display columns.           |
| `organizations`, `organization_members`     | Fashion business identity and trusted member role. New workspace creation is an atomic authenticated RPC.                             |
| `platform_admins`                           | Separate protected server-read authorization for platform operators; no browser grants.                                               |
| `garments`, `assets`                        | Original garments, private object metadata, thumbnails and expiry. Originals remain separate from generated content.                  |
| `customers`                                 | Minimal workspace-owned customer metadata.                                                                                            |
| `generation_jobs`, `generation_outputs`     | Immutable quoted charge snapshot, provider request reference, state, input references and transferred output references.              |
| `try_on_sessions`, `consents`               | SHA-256 token digest, expiry/revocation, one-use accounting, consent version and withdrawal timestamps. Raw tokens are never stored.  |
| `credit_accounts`, `credit_ledger`          | Locked cached balances and append-only delta journal.                                                                                 |
| `credit_packages`, `generation_price_rules` | Server-owned integer retail prices and provider usage/cost estimates. Published price columns exclude internal cost data.             |
| `payment_transactions`, `webhook_events`    | Expected payment snapshot, verified settlement/refund state and durable event deduplication. Raw payment card details are not stored. |
| `job_outbox`                                | Job dispatch intent committed in the same transaction as the reservation.                                                             |
| `media_upload_intents`                      | Bounded, service-only recovery records for abandoned private object uploads.                                                          |
| `privacy_requests`, `audit_logs`            | Pending privacy operations and protected minimal audit records.                                                                       |
| `rate_limit_windows`                        | Shared database rate counters; cleanup removes obsolete windows.                                                                      |

UUID primary keys, tenant foreign keys, unique idempotency constraints and query indexes are defined in the migration. Composite `(record_id, organization_id)` foreign keys prevent attaching one workspace's asset/garment/job to another. UUID input arrays are validated explicitly during reservation. Each private storage key must start with its organization UUID. Thumbnail and upload intent paths are generated by trusted server storage code, never accepted from a client.

Every application table enables Row Level Security. Anonymous visitors can read the retail catalog columns; guest try-on access is through a narrowly authorized server endpoint. Tenant reads require verified membership in a non-deleted organization. All entity mutations, storage operations and financial/job changes go through server authorization and service-only writes/RPCs. This intentionally prevents a browser from bypassing application validation with a direct Supabase write. No private bucket client access policies are installed. Storage URLs are short lived and issued after operation-specific authorization.

## Roles

| Role                   | Read workspace                      | Garments and content             | Start generation / customer links | Billing / member and workspace management |
| ---------------------- | ----------------------------------- | -------------------------------- | --------------------------------- | ----------------------------------------- |
| Owner                  | Yes                                 | Yes                              | Yes                               | Yes                                       |
| Admin                  | Yes                                 | Yes                              | Yes                               | Yes                                       |
| Designer               | Yes                                 | Yes                              | Yes                               | No                                        |
| Assistant              | Yes                                 | No privileged mutations          | No                                | No                                        |
| Guest customer         | Its authorized session only         | Its authorized input/result only | One consented session             | No                                        |
| Platform administrator | Separately verified operator access | Audited operational actions      | Reconciliation only               | Protected administrative RPCs             |

The server policies in `src/server/auth` determine operation permissions. Database authenticated grants deliberately omit insert/delete and monetary function execution. A workspace role never grants platform administration. Provision platform administrators using a controlled service/SQL session by inserting the verified Auth UUID in `platform_admins`; no signup metadata field or browser control can mint that role.

## Transactional functions

- `create_organization(p_name)` uses `auth.uid()`, inserts owner membership and a zero-balance account atomically, and bounds owned workspace count.
- `reserve_generation(...)` locks the account, checks trusted actor membership or valid consented guest session, rechecks sources and reviewed price, compares expected quote values, checks daily spending/active job limits, records one job, ledger reservation and outbox entry atomically. Guest usage is consumed in that transaction.
- `claim_generation(...)` serializes provider slot claims with a transaction advisory lock. Three global in-flight jobs and one per organization are permitted. Submitting/processing and ambiguous submission holds count as occupied slots even across worker sleeps/restarts.
- `finalize_generation(...)` locks job/account and settles once only after the expected generated asset kind exists, or releases credits once for failure. Original garment assets cannot satisfy successful settlement.
- `expire_unsubmitted_generations(cutoff)` locks at most 50 safely unsubmitted old jobs and releases their reservations. Ambiguous submission holds are excluded.
- `settle_payment(...)` locks the purchase and account; verifies expected amount/currency/domain/email; issues one ledger entry and credit increment. Duplicate events return the same settled row.
- `prepare_payment_refund(...)` requires a protected platform administrator and all package credits available. It removes the credits and marks the purchase pending before permitting one external refund request. `finalize_payment_refund(...)` records independently verified processed refund data.
- `admin_adjust_credits(...)` requires protected operator identity, a bounded non-zero integer amount, reason and idempotency key. It appends a compensating entry with audit.
- `consume_rate_limit(...)` increments a shared fixed-window counter atomically.

Security-definer functions set a fixed search path. Public function execution and schema CREATE are revoked. Financial/job RPC execution belongs only to `service_role`; the browser receives only the organization creation and read-policy helper functions. The ledger rejects UPDATE/DELETE even by normal elevated application code. Backups and deliberate migration operations remain infrastructure responsibilities.

## Verification evidence and limits

`npm run db:validate` executes the actual SQL and seed using PGlite's embedded PostgreSQL. The harness supplies minimal `auth.users`, `auth.uid()`, roles and `storage.buckets` objects because managed Supabase services are unavailable in the local environment. Tests exercise actual PostgreSQL constraints, RLS, grants, RPC state changes, idempotency, balance invariants, failed reservations, guest expiry/revocation/withdrawal and provider slot limits.

This validates application SQL locally. It does **not** verify a hosted Supabase API, Auth email delivery, Supabase Storage/RLS end-to-end, independent PostgreSQL connections, remote backups or multi-process lock contention. PGlite serializes Promise-based concurrent requests through one local engine. Before launch, repeat race tests using independent clients against the staging PostgreSQL database, run the Supabase database linter, and execute the credentialed two-tenant browser/security suite. Never report these local tests as live integration tests.
